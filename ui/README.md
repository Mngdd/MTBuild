# MTBuild GUI

Десктопный GUI поверх `internal/mesher` (того же контракта, что использует
`cmd/mtbuild-cli`), написан на [Gio](https://gioui.org) — immediate-mode
GUI-тулкит, чистый Go, без webview/Electron/браузера. Рендер идёт напрямую
через GPU-бэкенд ОС (на Windows — Direct3D/OpenGL через ANGLE), окно и
алгоритм построения сетки живут в одном процессе: GUI просто вызывает
`mesher.Mesher.Generate` в горутине, никакого HTTP/WS-моста нет.

Запуск:

```bash
go run ./ui
```

---

## Как это всё устроено в целом

Gio — immediate-mode: нет дерева виджетов, которое где-то живёт между
кадрами. Каждый кадр весь UI строится заново функциями вида
`Layout(gtx layout.Context, ...) layout.Dimensions`, которые одновременно
и считают размеры, и пишут инструкции отрисовки в буфер `op.Ops`. Всё, что
должно "помнить" себя между кадрами (текущий выбор, введённый текст,
активна ли загрузка файла) — это обычные Go-поля в обычных структурах,
которые нужно создать **один раз до цикла** и переиспользовать каждый кадр.

Отсюда восемь файлов пакета `main`:

| Файл | Что содержит |
|---|---|
| [main.go](main.go) | Точка входа, окно, единственный event-loop |
| [algos.go](algos.go) | `sidebarState` — весь левый столбец целиком |
| [dock.go](dock.go) | `dockPanel` — выдвижная панель у края (сайдбар слева, метрики снизу): размер мышью, сворачивание в полоску; `dragGrip` — перетаскиваемая ручка |
| [metrics.go](metrics.go) | `metricsPanel` — нижняя панель метрик: короткий/подробный режим, графики по итерациям, живые метрики сетки |
| [geoms.go](geoms.go) | `geomState` — выбор контура (пресет/DXF): верхнее меню + floating-панель |
| [params.go](params.go) | `paramsState`/`paramCtrl` — слайдеры+числа и чекбоксы параметров алгоритма |
| [run.go](run.go) | `runState` — Start/Stop, фоновый расчёт, итоговые метрики и история метрик по ходу расчёта |
| [view.go](view.go) | `meshView` — векторный просмотр готовой сетки: зум, сдвиг, сброс вида |

Дерево владения (кто кого создаёт и хранит):

```
main.run()
 ├─ dockPanel (sidebarDock) — ширина сайдбара, свёрнут ли он; рисует sb и rs.contentView рядом
 ├─ sidebarState (sb)
 │   ├─ paramsState        — параметры каждого зарегистрированного алгоритма
 │   ├─ geomState (sb.geom) — контур: пресет/DXF, дропдаун, загрузка файла
 │   ├─ hoverScrollList ×2 — свой скролл у списка алгоритмов и у настроек
 │   └─ dragGrip (listSplit) — граница между ними
 └─ runState (rs)          — Start/Stop, канал результата, метрики
     ├─ meshView (rs.view) — последняя сетка + камера (зум/сдвиг)
     ├─ progressSink (rs.progress) — счётчик итераций и история метрик текущего запуска
     └─ metricsPanel (rs.panel) — нижняя панель метрик со своим dockPanel
```

`geomState` физически хранится внутри `sidebarState` (создан в
`newSidebarState`), но это не значит, что и рисуется он только там: у него
три точки входа в вёрстку, вызываемые из разных мест дерева —
`sb.geom.MenuBar` и `sb.geom.Overlay` main.go зовёт напрямую (первую — как
часть верхней строки окна, вторую — последней, поверх всего), а
`sb.geom.Notice` зовёт уже сам `sidebarState.Layout` изнутри сайдбара.
Владение (где объект живёт) и место в вёрстке (где он рисуется) — разные
вещи, и тут они разошлись сознательно: подробности в разделе про geoms.go.

`sb.Layout` получает `rs` параметром (не хранит поле) — так Start-кнопка
внутри сайдбара может дёрнуть `rs.start(...)`, а `rs.contentView` рисуется
отдельно, в правой панели.

## Сквозные приёмы

Пять вещей повторяются во всех файлах (четыре техники и одни грабли);
проще один раз понять их тут, чем в каждом файле заново.

### 1. Горутина → канал → `poll()`

Всё, что блокирует (расчёт сетки, системный диалог выбора файла), нельзя
звать из горутины event-loop'а — окно зависнет. Но трогать состояние можно
только из неё же — иначе гонка данных. Канал — единственный мост:

```
клик → go func() {
    результат := тяжёлая_операция()
    ch <- результат
    win.Invalidate()   // разбудить event-loop
}()
                                          │
                    следующий FrameEvent ◄┘
                            │
                poll(): select { case r := <-ch: ...; default: }
```

Используется дважды: `runState.start`/`poll` (сам расчёт меша) и
`geomState.startLoad`/`poll` (диалог выбора `.dxf`).

### 2. "Скрытый" элемент = отсутствие в списке, а не флаг

И алгоритмы (`algoOrder` в algos.go), и контуры (`geomOrder` в geoms.go)
устроены так: реестр (`mesher.registry`, `geometry.Preset`) может содержать
больше вариантов, чем показывает GUI. Видимость — это просто присутствие
имени в срезе `algoOrder`/`geomOrder`. Никакого `Hidden bool` нигде нет:
если что-то не добавлено в этот срез, оно физически не может отрисоваться.

### 3. Фон под контентом, размером точно по контенту

У Gio нет "background size to content" из коробки. Приём (numberBox в
params.go, outputBadge в algos.go, panel в geoms.go): записать контент в
`op.Record`, узнать его реальный размер из возвращённых `Dimensions`,
нарисовать фон/рамку этого размера, потом воспроизвести записанный контент
поверх:

```go
macro := op.Record(gtx.Ops)
dims := <разложить контент>
call := macro.Stop()
paint.FillShape(gtx.Ops, bg, clip.Rect{Max: dims.Size}.Op()) // фон под точный размер
call.Add(gtx.Ops)                                            // контент поверх
```

Там, где фон — просто вся доступная область (без авто-размера), проще:
`layout.Stack{}.Layout(gtx, layout.Expanded(рисуетФон), layout.Stacked(контент))`
— так сделаны строки списков (`algoRow`, `dropdownRow`). `MenuBar` этот
`Stack` не использует вовсе — там фон просто во весь бар, а подсветка
пункта меню маленькая и по размеру текста, так что проще последовательным
`paint.FillShape` без всякого `Stack`.

### 4. Порядок отрисовки = порядок обработки кликов

В Gio нет отдельного z-index — то, что записано в `op.Ops` позже, и рисуется
позже (поверх), и **выигрывает при попадании клика**, если области
пересекаются. Это не деталь реализации, а то, на чём построен весь floating
dropdown в geoms.go: `Overlay` рисуется из корня (main.go) **после** всего
остального интерфейса → невидимый backdrop на всё окно перехватывает клики
"мимо" у всего, что было нарисовано раньше → а сама панель дропдауна,
записанная ещё позже, перехватывает клики у backdrop'а в своих границах.
Один и тот же принцип, три уровня приоритета.

### 5. `Stack` обнуляет `Min` своим `Stacked`-детям — грабли, не приём

Не техника, а конкретная засада, на которую наступили дважды (`algoRow`,
`dropdownRow`): казалось бы, задать `gtx.Constraints.Min.X = gtx.Constraints.Max.X`
перед вызовом `layout.Stack{}.Layout(...)` должно заставить фон (`Expanded`)
покрывать всю ширину строки. Не заставляет — в исходнике Gio
(`layout/stack.go`) `Stack.Layout` перед раскладкой `Stacked`-детей делает
`cgtx.Constraints.Min = image.Point{}`, то есть обнуляет `Min` именно для
них. Если контент внутри `Stacked` — это `Flex` без единого `Flexed`
(только `Rigid`), он честно сжимается по контенту, а `Expanded`-фон потом
подстраивается под этот уже узкий размер. Снаружи это выглядит как "клик
работает по всей строке, а подсветка обрывается на конце текста" — так
он и был обнаружен.

Фикс — поставить `gtx.Constraints.Min.X = gtx.Constraints.Max.X` заново,
**внутри** самого `Stacked`-колбэка, а не полагаться, что снаружи заданное
значение туда дойдёт.

## main.go

Точка входа. `main()` — создаёт `*app.Window`, задаёт заголовок/размер/иконку
(иконка — не рантайм-опция Gio на Windows, а `ui/rsrc_windows_amd64.syso`,
сгенерированный из `data/favicon_transp.ico` тулом `rsrc`; компилятор Go
линкует любой `.syso` рядом с пакетом автоматически; поменяли картинку —
пересобрать: `go run github.com/akavel/rsrc@latest -ico
data/favicon_transp.ico -o ui/rsrc_windows_amd64.syso`), запускает `run(w)` в горутине
(так требует `app.Main()` — см. ниже), и по её завершении зовёт `os.Exit`.

`run(w)` — сам event-loop:

```go
var ops op.Ops                    // один буфер на всю программу, не на кадр
for {
    evt := w.Event()              // блокируется до следующего события
    sb.geom.ListenEvents(evt)     // explorer должен видеть ВСЕ события
    switch e := evt.(type) {
    case app.DestroyEvent:
        return e.Err              // окно закрыто; Err нужен наверх, см. ниже
    case app.FrameEvent:
        rs.poll(); sb.geom.poll() // забрать готовые фоновые результаты
        gtx := app.NewContext(&ops, e)
        layout.Stack{}.Layout(gtx,
            layout.Stacked(func(gtx) ... {
                // Vertical: меню-бар сверху (Rigid), под ним —
                // сайдбар+контент рядом (Flexed(1) с panel.Layout внутри)
            }),
            layout.Expanded(...), // sb.geom.Overlay поверх вообще всего
        )
        e.Frame(gtx.Ops)          // отдать кадр на реальную отрисовку
    }
}
```

Детали, которые не очевидны с первого взгляда:

- **`var ops op.Ops` вне цикла.** `app.NewContext` сам вызывает `ops.Reset()`
  каждый кадр — это чистит содержимое, но не память. Объявление внутри `for`
  означало бы новую аллокацию буфера на каждый кадр вместо переиспользования
  уже выросшего под нужный размер куска памяти.
- **`return e.Err`, а не `os.Exit` прямо тут.** `DestroyEvent.Err` — `nil`
  при обычном закрытии окна, не-`nil` при аварийном. Это осознанно отдаётся
  вызывающему коду (`main()`), а не проглатывается — иначе краш выглядел бы
  как нормальное закрытие, и `os.Exit(0)`/`os.Exit(1)` в `main()` не мог бы
  их различить.
- **Почему в `switch` только 2 кейса.** `w.Event()` может вернуть и другие
  типы (`app.ConfigEvent` — изменилась конфигурация окна, `app.ClosingEvent`
  — юзер нажал крестик, можно вызвать `.Abort()` и не закрывать окно,
  `app.Win32ViewEvent` — нативный хендл окна). Необработанные варианты в Go
  type switch просто молча пролетают мимо `switch`, это штатное поведение,
  не ошибка. `Win32ViewEvent` при этом не теряется — его читает
  `sb.geom.ListenEvents(evt)`, вызванный **до** `switch`, вне зависимости от
  типа: `explorer` сам вылавливает то событие, что ему нужно для диалога.

## algos.go — `sidebarState`

Весь левый столбец. Порядок сверху вниз в `Layout`:

1. `s.geom.Notice(...)` — строка с ошибкой загрузки DXF, если она есть;
   схлопывается в `layout.Dimensions{}` (нулевой размер), если ошибки нет.
   Сам выбор контура сюда больше не относится — он теперь window-level
   меню (`geomState.MenuBar`, рисуется из main.go, см. geoms.go).
2. `splitLists` (`layout.Flexed(1, ...)`): сверху список алгоритмов,
   снизу `detailPanel` выбранного, у каждого свой `widget.List` (скролл), а
   между ними ручка `listSplit`, которой двигают границу. Высота списка
   алгоритмов — `algoListHeight`, зажата так, чтобы всегда были видны хотя
   бы одна строка алгоритма и `minDetailHeight` настроек, и не больше
   высоты всех строк (пустоту под списком растягивать незачем). Оба
   списка — `hoverScrollList`: полоса прокрутки видна, только пока мышь
   над этим списком (или полосу тащат). Наведение ловит область на весь
   список, зарегистрированная до него, — она предок всего внутри, а предки
   в Gio получают события вместе с детьми, так что строки и ползунки это
   не ломает. Место под полосу зарезервировано всегда, прячется только её
   цвет — иначе содержимое прыгало бы вбок при каждом наведении. Скролл у
   настроек не просто так — у sph-quadtree 7 параметров, на невысоком окне
   это легко не помещается по вертикали, и без скролла кнопки Start/Stop
   выталкивались за нижний край окна (было именно так на раннем этапе).
3. Start/Stop (`rs.Layout(...)`) — Rigid, всегда виден, вне скроллов.
   Кнопки расположены одна под другой на всю ширину сайдбара
   (`layout.Flex{Axis: Vertical}`, каждая — `Rigid` с
   `gtx.Constraints.Min.X = gtx.Constraints.Max.X`), не рядом 50/50.

**`algoOrder`/`algoMetas`** — презентационные данные (лейбл, описание,
`Output: "triangular"|"polygonal"`), которых нет в самом контракте
`mesher.Mesher` (там только `Name()`/`Params()`/`Generate()`). Так и
задумано: GUI не должен лезть в домен, а домену не нужно ничего знать про
то, как он показывается. Три алгоритма сейчас: `sph-quadtree`, `grid` —
оба треугольные (`Mesh.Triangles`); `charge-voronoi` — многоугольный
(`Mesh.Cells`, `Output: "polygonal"`, красный/янтарный бейдж вместо синего).
Регистрация в реестре (`init()` в самом пакете алгоритма) и видимость в GUI
(`algoOrder`) — разные вещи: пакет алгоритма подключается анонимным
импортом в main.go (`_ "MTBuild/internal/mesher/charge"`) именно ради
побочного эффекта `init()`, а `algoOrder` — что из зарегистрированного
реально показать. Забыть анонимный импорт при добавлении нового алгоритма
в `algoOrder` — паника при старте (`newParamsState`: "algoOrder names an
unregistered mesher"), а не тихая пустая строка в списке.

**`algoRow`** — одна строка списка: `widget.Clickable` меняет
`s.selected`, подсветка (акцентная полоса слева + тон фона) через
приём №3 выше. Клик проверяется **до** отрисовки (`click.Clicked(gtx)`),
это общий для всего проекта порядок — событие от предыдущего кадра
обрабатывается в начале следующего.

**`detailPanel`** — имя + `outputBadge` (цветной бейдж
"треугольная"/"многоугольная", приём №3) + описание + `paramsList`. Имя и
бейдж ставит `flowRow`: рядом, если влезают в ширину, иначе бейдж
уезжает строкой ниже — панель можно сузить, и он не должен налезать на
имя. `flowRow` общий: им же раскладывается шапка панели метрик — элементы
слева направо, а не влезающий переносится на новую строку (заранее
раскладывает всех в `op.Record`, чтобы знать ширины, — приём №3). В строке `algoRow` по той же причине `MaxLines = 1`: длинное имя
обрезается с «…», а не переносится из строки фиксированной высоты.

**`paramsList`** — тонкая обёртка: достаёт `*algoParams` для
`s.selected` из `s.params` (params.go) и раскладывает его контролы
вертикально, пропуская скрытые (`algoParams.visible`); параметр с
`DependsOn` рисуется с отступом слева под своим чекбоксом. Вся логика
самих контролов — в params.go, тут только вёрстка.

## dock.go — `dockPanel`, `dragGrip`

**`dockPanel.Layout`** — делит место на основную область и панель,
прижатую к краю (`edge`: `dockLeft` — сайдбар, `dockBottom` — метрики), и
рисует между ними линию-разделитель. Размер панели тянут мышью:

- от минимума (`minSize`, параметр `Layout`) до `maxFraction` места панель
  просто следует за мышью;
- меньше минимума — стоит на минимуме, а линия краснеет (`squeezed`);
- меньше `minSize * collapseFraction` (половины минимума) — сворачивается в
  полоску `collapsedStripSize` с тёмной стрелкой туда, куда панель
  выдвигается (вправо у сайдбара, вверх у метрик). Запас между минимумом и
  порогом — чтобы не схлопнуть панель случайно;
- в том же перетаскивании можно передумать и вытянуть обратно.

Свёрнутую полоску можно кликнуть (панель вернётся с последним размером) или
вытянуть. Пока панель развёрнута, полоски нет. Ручка у разделителя и у
полоски **одна и та же** (`p.grip`): схватили полоску, панель развернулась —
и дальше тот же жест уже тянет разделитель. Gio продолжает слать события
тому, кто получил нажатие, пока его тег регистрируется каждый кадр, — а
какой при этом прямоугольник, ему всё равно.

Код один на оба края: всё считается «вдоль оси» (`splitAt` — где
разделитель при данном размере панели, `panelSizeAt` — обратно, `along` —
прямоугольник от и до вдоль оси), а разница краёв — в этих трёх функциях:
снизу размер панели отсчитывается от нижнего края, а не от начала.

Минимум сайдбара — константа `minSidebarWidth`; минимум панели метрик —
высота её шапки на прошлом кадре плюс `metricsPeek` (кусок первой строки
метрик), потому что шапка с кнопками может переноситься на узком окне.
`ensureAtLeast` растит развёрнутую панель — так панель метрик сама
подрастает при включении подробного режима.

Ручка ловит мышь шире видимой линии (`splitGripInside`/`splitGripOutside`),
и почти вся — со стороны основной области, над её полем: у края панели
стоят полосы прокрутки списков, их ручка перекрывать не должна.
Регистрируется последней — поверх и панели, и основной области (приём №4).

**`dragGrip`** — общая для всех разделителей (`dockPanel` и `listSplit` в
algos.go) разборка мыши: нажатие, перетаскивание дальше `clickSlop`,
отпускание; если мышь почти не сдвинулась — это клик. Главная тонкость —
**в каких координатах** её регистрировать. Позиции мыши Gio отдаёт в
координатах того места, где был `event.Op`. Если зарегистрировать ручку в
её собственных координатах (через `op.Offset` к ней), она каждый кадр
переезжает вслед за мышью, и курсор относительно неё почти стоит на месте.
Поэтому `layoutArea` получает прямоугольник в координатах неподвижного
контейнера (всего места `dockPanel`, области списков для `splitLists`), и
позиция мыши — это сразу желаемая позиция ручки, с поправкой
`grabOffset` на то, за какое место её схватили (чтобы не прыгала).

## metrics.go — `metricsPanel`

Нижняя панель под областью просмотра. Сама держит свой `dockPanel`
(`edge: dockBottom`): клики по кнопкам разбираются **до** раскладки dock,
чтобы панель, подросшая под подробный режим, раскрылась в том же кадре.

**Шапка** (`header`, через `flowRow`): "Метрики", серый разделитель и две
кнопки-переключателя `toggleButton` — в духе Start, но выключенная — только
контур акцентного цвета, включённая — залита. На `gtx.Disabled()` кнопка
серая и не нажимается.

- **«Подробный режим»** — переключает короткий режим (`compactGrid`: блоки
  одинаковой ширины "название ... число", сколько влезает в ряд) и
  подробный (`sidesHistogramCard` — только у многоугольной сетки, — и
  `chartGrid`: карточки одинаковой ширины с ломаной по итерациям).
- **«Живые метрики сетки»** (с ⚠ и подсказкой `tooltipBelow` при
  наведении) — строить ли сетку каждые 10 итераций ради её метрик. Читается
  в момент Start (`runState.start` кладёт её в `progressSink.liveMesh`),
  поэтому на время расчёта кнопка серая: переключение посреди расчёта
  смешало бы на одном графике живую и неживую историю.

**Что считается.** Метрики частиц (`mesher.ParticleMetrics`: сдвиг за шаг
в долях целевого размера, разброс расстояний до ближайшего соседа) — в
каждом кадре всегда, они дешёвые. Метрики сетки (`mesh.QualityMetrics` или
`mesh.PolyQualityMetrics`) — в кадре только с живыми метриками, иначе
только в конце: тогда во время расчёта у них "—" и "посчитается в конце", а
после — ровная линия на итоговом значении (тем же цветом, что и живые). У
алгоритма без итераций (Grid) метрик частиц нет совсем, а у метрик сетки
подпись "без итераций".

**Данные** приходят готовыми в `metricsView` (собирает
`runState.metricsView`): идёт ли расчёт, форма сетки, история `samples`
(по `metricSample` на кадр) и итог `final`. Список метрик — таблицы
`triMetricDefs`/`polyMetricDefs` (`metricDef`: подпись, описание, по сетке
или по частицам, как достать значение из `metricSample`, fmt-шаблон);
добавить метрику — добавить строку в таблицу. `metricSeries` собирает
точки графика, `current` — текущее значение.

**Значок (i)** у названия (`metricTitle`) — серая `icons.ActionInfo`; при
наведении (`gesture.Hover`, по одному на название — живут в
`p.infoHovers`, потому что состояние наведения должно пережить кадр) под
ним всплывает `metricDef.description`. Название обрезается с «…», значок
остаётся. Подсказка рисуется через `op.Defer` поверх всего (`tooltipBelow`)
и не вылезает за правый край панели: `layoutGrid` сообщает каждой ячейке,
сколько места правее неё (`roomRight`), и подсказка у правой колонки
сдвигается влево.

**Вёрстка.** `layoutGrid` — ячейки равной ширины рядами (колонок —
сколько влезает с шириной не меньше заданной), `lineChart` — ломаная
`clip.Stroke` по точкам, ось y — от минимума до максимума точек (ровная
линия — посередине), `histogram` — столбики с подписями. Тело панели
скроллится только по вертикали (`hoverScrollList`), шапка — нет.

## geoms.go — `geomState`

Выбор контура (эллипс/круг/Zalesak/крыло из `.dxf`, или свой файл).

**`geomOrder`/`geomLabels`** — тот же приём видимости, что у `algoOrder`:
что не в списке, того не существует для GUI, даже если `geometry.Preset`
такое имя бы принял.

**Состояние** (`geomState`) хранит уже готовую `current geometry.Geometry`
(не просто имя пресета) — потому что после загрузки своего DXF источник
геометрии больше не сводится к строковому ключу. `presetName` — отдельно,
только чтобы подсветить нужную строку в дропдауне (`""`, если геометрия
из загруженного файла, а не из пресета).

**`newGeomState(w)`** создаёт `explorer.NewExplorer(w)` — обёртку gio-x над
нативным диалогом выбора файла (`gioui.org/x/explorer`, официальное
расширение Gio, чистый Go, без cgo — на Windows дергает WinAPI напрямую
через сисколлы). Привязана к конкретному окну, создаётся один раз.

**`selectPreset(name)`** — синхронный вызов `geometry.Preset(name)`. Паника
при ошибке осознанная: сюда попадают только наши же хардкоженные имена из
`geomOrder`, ошибка тут — баг в этом файле, а не что-то, что мог вызвать
пользователь.

**`startLoad()`** — горутина: `explorer.ChooseFile(".dxf")` блокируется,
пока не закроется системный диалог, поэтому не может звать её из
event-loop'а напрямую (приём №1). Дальше — `io.ReadAll` +
`geometry.LoadDXF` (тот же парсер, что использует CLI и
`geometry.Preset("wing")`, который вшивает `testdata/kulman.dxf` через
`go:embed`) + `.Normalized()`, чтобы своя геометрия вела себя в алгоритмах
так же, как пресеты (все параметры sph-quadtree откалиброваны в долях
unit-bbox).

**`MenuBar`** — сам пункт меню, вызывается из main.go **над** сайдбаром и
контентом, во всю ширину окна (Rigid-строка высотой `menuBarHeight`). Это
осознанная переделка: раньше выбор контура жил баром-комбобоксом внутри
сайдбара (растянутым на всю его ширину, с рамкой), но так меню не выглядят
ни в одном обычном Windows-приложении — меню сидит своей строкой в самом
верху окна, размером по своей подписи, а не во всю ширину. Сейчас это флет
кликабельный текст "Фигура: <label>" с подсветкой по размеру текста при
hover/открытии (тот же приём №3 — record/measure/paint-behind), без рамки
и без стрелочки — визуально ровно как "Файл"/"Правка" в нативных
приложениях.

**`Notice`** — отдельно от `MenuBar`: последняя ошибка `startLoad`, если
есть. Рисуется из сайдбара (algos.go), не из окна — это фидбэк про то, что
подгрузилось в сайдбар, логически ему и принадлежит, а не меню.

Сам дропдаун — это **`Overlay`**, отдельный метод, вызываемый из main.go
последним (приём №4): невидимый `backdropClick` на всё окно (клик мимо
закрывает панель) + сама панель (`panel`/`panelRows`), позиционированная
через `op.Offset` на фиксированное смещение от левого верхнего угла окна
(`menuBarHeight` по Y, чтобы панель начиналась сразу под меню-баром;
ширина — своя константа `panelWidth`, больше не завязанная на ширину
сайдбара, потому что триггер меню теперь никак не связан с сайдбаром
физически).

## params.go — `paramsState` / `paramCtrl`

Динамические контролы параметров, построенные из `mesher.ParamSpec`
(`Key`/`Label`/`Min`/`Max`/`Def`/`Step`) — никакого знания о конкретном
алгоритме тут нет, один и тот же код обслуживает и 7 параметров
sph-quadtree, и 1 параметр grid.

**`paramCtrl`** — одна пара слайдер+число на один `ParamSpec`.
`widget.Float` в Gio умеет только диапазон `[0,1]`, поэтому пересчёт в
реальные `[Min,Max]` и обратно — на `paramCtrl.value()`/`setValue()`.
Слайдер и текстовое поле синхронизированы в обе стороны:

- слайдер потянули → `Layout` замечает, что `float.Value` изменился с
  начала кадра, и обновляет текст в `editor` — но только если `editor` не
  в фокусе (иначе слайдер бы стирал то, что человек как раз печатает);
- в поле ввели число и нажали Enter (`widget.SubmitEvent`) → парсим,
  зажимаем в `[Min,Max]`, зовём `setValue` — оно обновляет и слайдер, и
  переформатирует текст (например `"0.05"` вместо `"0.0500001"`);
- если ввели не число — `setValue` откатывает поле к последнему валидному
  значению, ничего не падает.

**`formatParam(v, step)`** — число знаков после запятой берётся из `Step`
(`0.005` → 3 знака, `10` → целое), чтобы в поле никогда не показывалось
больше точности, чем реально различает слайдер.

**Флаги (`Kind == mesher.KindBool`)** — вместо слайдера `material.CheckBox`
на `paramCtrl.check`; `value()` отдаёт 1/0. **`DependsOn`** — параметр
виден только пока отмечен указанный флаг (`algoParams.visible`).
`values()` всё равно отдаёт и скрытые значения — читать их или нет, решает
алгоритм по флагу. `newAlgoParams` паникует, если `DependsOn` ссылается на
несуществующий ключ или не на флаг (иначе контрол молча не появился бы).

**`newParamsState()`** строит контролы для **всех** алгоритмов из
`algoOrder` сразу при старте (не лениво при первом выборе) — так простое
переключение между алгоритмами в сайдбаре не теряет то, что накрутили на
предыдущем, пока открыто окно.

## run.go — `runState`

Start/Stop и жизненный цикл одного запуска.

**`start(algoName, geom, params)`** — горутина: `mesher.New(algoName)` (тот
же реестр, что у CLI) → `algo.Generate(ctx, geom, params, progress)` → в
`resultCh` уходит сама сетка и контур, без всякой растеризации: рисует её
`meshView` (view.go) векторно, каждый кадр.

**`progressSink`** — sink текущего запуска. Из снапшотов берёт номер
итерации и `Frame.TotalIters` (атомики — пишет горутина `Generate`) и будит
окно не чаще `titleRefresh` (100 мс). `poll()` по ним ставит заголовок окна
`MTBuild (130/300)`, пока идёт итерационная стадия, и просто `MTBuild`, когда
расчёт закончен или не запущен. Алгоритмы отчитываются раз в 10 итераций,
так что счётчик идёт шагами по 10. Сами частицы из снапшотов пока не
рисуются (см. «Чего тут нет»).

Ещё `progressSink` копит историю метрик для панели метрик: из каждого
кадра — `Frame.Particle`, а с живыми метриками сетки ещё и строит сетку
(`Frame.BuildMesh`) и меряет её — прямо в `Snapshot`, в горутине расчёта,
пока частицы стоят (этим живые метрики и замедляют расчёт). История под
мьютексом; `poll()` каждый кадр забирает её копию в `r.samples`.

Какие итоговые метрики — зависит от `m.Polygonal` (флаг выставляет сам
алгоритм): `mesh.QualityMetrics` (уже посчитаны, `Generate` их и вернул)
для треугольной сетки; `mesh.EvaluatePoly(m)` для полигональной
(`charge-voronoi` — его `Generate` отдаёт `QualityMetrics{}`, нули, эти
числа не для неё). Форма сетки нужна панели метрик уже во время расчёта,
поэтому `start` ставит `r.polygonal` сразу — из `algoMetas`, а `hasFinal`
говорит, что итоговые метрики относятся к последнему запуску.

**`stop()`** дёргает `context.CancelFunc` — алгоритмы проверяют `ctx.Err()`
по ходу работы (внутри `sph.Relax`), так что реально прерывает расчёт, а
не просто блокирует кнопку в интерфейсе.

**`Layout`** — сами кнопки, одна под другой на всю ширину (`Flex{Vertical}`,
`Rigid`+`Rigid`, без `Flexed` — ширину каждая берёт явным
`gtx.Constraints.Min.X = gtx.Constraints.Max.X`, а не через грабли из
приёма №5 — тут нет `Stack`, так что и обнулять нечего). Задизейблены через
`gtx.Disabled()` (Gio-стиль: копия `gtx` с отключённым вводом —
`material.Button` сама красит себя приглушённым цветом и игнорирует клики,
если ей передать такой `gtx`), а не булевым полем на кнопке.

**`contentView`** — правая панель: область просмотра (`viewArea`) с
панелью метрик (`r.panel`, metrics.go) под ней. `viewArea` — 4 состояния
по приоритету: ошибка → есть сетка (`rs.view.Layout`) → идёт расчёт →
пусто (`idleView`: логотип и под ним "Нажмите Start").

**`idleView`** — стартовый экран. Логотип — `data.LogoPNG`
(`data/logo-transp.png`, вшит в бинарник через `go:embed` в пакете
`MTBuild/data`: сам `ui/` вшить файл из соседней папки не может),
декодируется один раз в `logoImage`. Он квадратный и вдвое шире надписи —
а ширину надписи заранее не знаешь, поэтому надпись сначала раскладывается
в `op.Record` (узнать размер), затем рисуется логотип нужного размера, а
записанная надпись воспроизводится под ним. В низком окне логотип
ужимается, чтобы влезть вместе с надписью.

## view.go — `meshView`

Просмотр готовой сетки с камерой. Хранит сетку как есть (вершины +
треугольники/ячейки) и контур, и каждый кадр перерисовывает их путями Gio
(`clip.Path`) прямо в экранных координатах. Отсюда оба свойства, ради
которых он сделан вместо картинки: зум не мылит (векторный рендер на GPU в
любом масштабе), а толщина линий на экране постоянна при любом зуме (точки
переводятся в пиксели до обводки, а не масштабируется уже обведённое).

**Камера** — два числа: `zoom` (множитель поверх "вписать целиком", 1 —
исходный вид) и `pan` (сдвиг в пикселях). `worldToScreen` собирает из них
перевод мир→пиксели: вписать bbox контура в холст с полем `fitMargin`,
умножить на `zoom`, сдвинуть на `pan`, перевернуть Y (у мира вверх, у
экрана вниз — как в SVG).

**Ввод** (`handleInput`) — свой `pointer.Filter` на весь холст: нажатие
левой кнопки начинает перетаскивание, `Drag` прибавляет смещение курсора к
`pan`, колесо зовёт `zoomAt`. `scrollAnyAmount` в фильтре — без него Gio
не отдал бы событие колеса этому обработчику. Курсор над холстом —
"рука" (`CursorGrab`, при перетаскивании `CursorGrabbing`).

**`zoomAt`** — зум к курсору: точка сетки под курсором остаётся под ним.
Шаг — `zoomPerNotch` (×1.15) за щелчок колеса; на Windows щелчок даёт
`Scroll.Y = ±120` (сырое `WM_MOUSEWHEEL`, вверх — отрицательное), дробные
значения тачпада дают дробный шаг. Ограничен `minZoom..maxZoom`. Формула:
курсор сейчас на `cursorFromOrigin` пикселей от точки, куда попадает центр
мира; после зума это расстояние вырастет в `newZoom/zoom` раз — `pan`
сдвигается ровно на столько, чтобы компенсировать.

**"Сбросить вид"** — кнопка в правом верхнем углу холста, `resetCamera()`
(zoom=1, pan=0). Рисуется после холста, поэтому клик по ней достаётся ей,
а не холсту (приём №4). Сама камера сбрасывается и при новом результате —
но только если сменился контур (`sameContour`: тот же ли срез `Outer`,
который держит `geomState`). Перезапуск на том же контуре с другими
параметрами оставляет зум и сдвиг — удобно сравнивать один и тот же
увеличенный участок.

**Отрисовка** (`drawMesh`) — четыре операции на всю сетку, а не по одной на
ячейку: заливка всех ячеек одним путём (`cellsPath`, `clip.Outline`),
обводка всех рёбер одним путём (`edgesPath`, `clip.Stroke`), поверх —
внешний контур и дырки (`contourPath`). Палитра та же, что у SVG-рендера.

**Центры ячеек** — только у многоугольной сетки (у треугольной частицы и
так совпадают с вершинами, центры там не рисуются). Два вида маркеров, оба
постоянного экранного размера и оба одним путём на всю сетку:
- красные крестики "×", поверх точек — частица-генератор ячейки, `mesh.Mesh.Sites`.
  Это поле заполняет сам алгоритм (сейчас только `charge`: по точке на
  ячейку, в том же порядке, что `Cells`); нет `Sites` или их число не
  совпадает с числом ячеек — крестиков нет. Размер — `siteCrossHalfSize`,
  толщина линий — `siteCrossWidth`; путь — `crossesAt`, у каждого крестика
  две диагонали отдельными отрезками (почему не одним контуром — см. ниже
  про рёбра);
- тёмные точки — центр масс ячейки (`polygonCentroid`, формула
  шнурка, а не среднее вершин; считаются один раз в `setMesh`). Радиус —
  `centroidRadius`, путь — `dotsPath`, каждая точка — 12-угольник.

Расстояние между крестиком и точкой — насколько разбиение не
центроидальное в этой ячейке. Крестик рисуется после точек, поэтому
виден целиком всегда, даже если точка прямо под ним.

Легенда — столбиком в левом верхнем углу холста (`dotLayer.legendItem`):
у каждого слоя глаз (иконки `ActionVisibility`/`ActionVisibilityOff` из
набора Material, который Gio и так тянет), маркер слоя (`drawCrossMarker` /
`drawDotMarker` — те же формы, что на холсте) и подпись; размеры —
`legendEyeSize`, `legendMarkerSize`, `legendTextSize`. Вся строка — одна
невидимая кнопка: клик в любое место строки (глаз, маркер, текст)
прячет/показывает слой. Состояние — `meshView.sitesLayer`/`centroidsLayer`
(`dotLayer`: флаг `hidden` + кнопка); при новом результате не
сбрасывается. Скрытый слой в легенде — перечёркнутый глаз и бледные маркер
с подписью. Легенда, как и "Сбросить вид", рисуется после холста, поэтому
клики по её строкам достаются ей.

**Почему рёбра — отдельным списком, а не обводка ячеек** — это грабли, на
которые наступили при переходе: если обвести `cellsPath` целиком, на экране
случайными кусками пропадают рёбра. Gio превращает обводку в контур и
заливает его по правилу nonzero; у двух соседних ячеек общее ребро
обводится дважды, и внутри одного пути эти перекрывающиеся полосы частично
гасят друг друга (выравнивание обхода всех ячеек не помогает — проверено).
Поэтому `setMesh` один раз считает `uniqueEdges` — каждое ребро ровно один
раз, пара индексов вершин, — и `edgesPath` рисует их отдельными открытыми
отрезками: у обводки одиночного отрезка ориентация от направления не
зависит, так что перекрытия в вершинах только складываются. Заодно
обводится вдвое меньше отрезков.

## Зависимости, которых нет в остальном проекте

```
gioui.org        — сам тулкит (layout/widget/text/op/gpu)
gioui.org/x       — расширения; из него используется только explorer
```

Транзитивно тянутся платформенные бэкенды `explorer` для всех ОС (Android
JNI, macOS/iOS Obj-C мосты, Linux D-Bus) — на Windows не используются в
рантайме, но нужны для компиляции пакета `gioui.org/x/explorer` как
таковой (файлы разделены по `_windows.go`/`_linux.go`/... суффиксам,
собирается только нужный).

## Чего тут осознанно нет

- **Живой просмотр итераций.** Из `Frame`-снапшотов берётся только счётчик
  итераций для заголовка; позиции частиц по ходу релаксации не рисуются.
  Картинка — только финальный результат.
- **Слайдер интервала у истории метрик.** Графики по итерациям есть (панель
  метрик), но всегда на весь расчёт — выбрать кусок или навести на точку
  нельзя.
- **Кэш и отсечение при просмотре.** `meshView` пересобирает пути всей сетки
  на каждый кадр (кадры у Gio идут только по событиям — при перетаскивании
  это каждое движение мыши) и не выкидывает ячейки за краем холста. Для
  сеток на тысячи ячеек это незаметно; если сетки вырастут на порядки,
  следующий шаг — отсекать невидимое и/или кэшировать пути до смены зума.
